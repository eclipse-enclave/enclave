1. Goal and constraints

Let agents running in separate enclave sessions delegate work to each other, with the same isolation guarantees a single session has today. The interaction must be:

  • Clean. A standard protocol, no file or git mailbox conventions, tool agnostic.
  • Performant. Local HTTP, no polling, final results only in the model's context.
  • Secure. No new host listeners, no shared network segment between peers, no host control capability inside a container, every message authenticated, authorized against host-provisioned identity, fail-closed on lost state, and audited.
  • Composable with terminal orchestration. Herdr or tmux remain the human's control plane. Enclave gains no daemon.

2. What enclave gives us today

  • Each session has its own labeled bridge network. In restricted mode the gateway sidecar is the attached endpoint and the tool container shares its network namespace. Unrestricted sessions (--allow-all-network) and the qemu backend have no gateway.
  • Session bridges are ordinary engine bridges, not internal networks: anything attached has a default route to the host gateway and from there to the internet. The gateway's own iptables rules are what restrict a session.
  • Restricted gateways set INPUT to DROP, admit loopback and established traffic, and accept each published port with a bare --dport rule on any interface (gateway-entrypoint.sh, setup_input_firewall). The same function runs for ip6tables, whose INPUT and OUTPUT policies are DROP. Egress is an ipset allowlist plus a NAT REDIRECT of ports 80 and 443 into the transparent proxy.
  • The gateway entrypoint stays resident as a root supervisor and reinstalls rules on SIGHUP, which network apply sends through the engine after rewriting the config bundle. The bundle is per project and tool (HostProjectGatewayConfigDir), shared by every session of that pair; session-specific values such as published ports reach the gateway through its environment, which cannot change after start.
  • Tool containers run with engine default capabilities (NET_RAW included on Docker); the gateway adds NET_ADMIN and NET_RAW.
  • Network teardown waits only for the session's own containers and treats any other endpoint as foreign (sessionOwnsEndpoints); garbage collection requires zero attached containers.
  • Podman networks are created with isolate=strict; older netavark falls back to isolate=true with a warning. Docker user bridges are isolated by the engine.
  • Named background sessions: enclave --background --name worker-1, with ps --json, attach, exec and stop. A foreground session's enclave process stays attached until the container exits. There is no daemon run mode. Cross-process locks live under ~/.local/state/enclave/locks/.
  • Persistent stores are host directories bind-mounted into containers, so the host can read a worker's store without the container running.
  • Tool config is injected through templates and patches, which is the path for adding an MCP server entry to a harness.
  • The docs state that container-to-container access is not a compatibility contract. A2A is therefore a new, explicit channel.

4. The A2A protocol, spec pin and carrier check

A2A (Agent2Agent, originally from Google, now a Linux Foundation project) is the open protocol for agents delegating work to agents.

Gate: no Go type is written before one tagged A2A release is pinned here, with version and spec URL. We speak the JSON-RPC binding only. Every method name, the agent card path, the task state list and the message and artifact shapes below must be validated against the pinned document. The names here are from memory of the 0.3 binding and the spec has moved since. Pinned version: A2A v1.0.1 (wire version 1.0), spec and normative proto; renames and shapes in spec-pin.md.
Agent card
JSON document under /.well-known/: name, description, skills, service URL, capabilities and security schemes. Cards served by the hub carry hub-facing URLs only (a2a.enclave:<port>/peers/<name>).
JSON-RPC 2.0 over HTTP
Send (request and response), stream (Server-Sent Events), get task, cancel task, resubscribe.
Task and context IDs
Issued by the worker adapter, as a normal A2A server, and persisted there. The hub translates nothing; it reads responses to cache ownership keyed by worker name and ID. Every request names its target worker, so IDs cannot collide across workers.
Task state machine
Submitted, working, completed, canceled, failed, rejected. Input-required and auth-required are not emitted in v1. No state is invented; see task endings.
Messages and artifacts
v1 accepts text parts only. Results arrive as artifacts.
Push notifications
Deferred. When added, the webhook URL points at the hub, which workers already reach over their egress rule.

If the pinned version lacks a legal carrier for any row, the design changes before implementation. Carrier check: passed against v1.0.1. Every row has a legal carrier; queue depth in the card needs a declared extension, and hub delivery errors use codes outside the -32001 to -32099 range A2A claims. Details and open items in spec-pin.md.

A2A is strictly client and server per task. That maps onto exclusive roles: the orchestrator is the client, workers are servers.

5. Topology: a hub on every member's bridge

One enclave-managed hub container per peer group. The hub has no network of its own. It is connected to each member's existing session bridge as an additional endpoint at join, with a static address assigned by the host inside that bridge's subnet, and disconnected at leave. Members never share a network segment.

  • No shared segment. Existing published-port INPUT rules stay unreachable to peers. ARP spoofing between members is impossible.
  • One policy and audit point per group.
  • Two scoped rules per member in the gateway, one NAT exemption, one DNS record.
  • No host listener.
  • Group isolation by topology. Two groups are two hubs; tokens are per group and per member.
  • Static hub addresses survive a hub container restart, so gateway overlays stay valid.
Gate P1: a multi-homed container under rootless Podman with netavark isolate=strict and under Docker, with the evidence list in scope. No fallback topology exists.

Conversation-set isolation

  • Between groups: separate hub, separate attachments, separate tokens.
  • Within a group: conversations are context IDs, each its own harness session in the worker. Tasks in one context share that transcript by design; two contexts never share one. All contexts of a worker share its container state (project mount, config store, memory, shell history), exactly as consecutive runs in one session do today.
  • Same project in several groups: isolated on the network and token level; per-project stores and the worktree are enclave's existing model. See the worktree guard.
  • Audit and names are per group. Session names are unique within a group.

6. The hub: processes, snapshot publication, commit

A small Go service built on the gateway base image, one instance per group. It is stateless beyond the host-published snapshot: membership, identity and credentials come from the host, task bookkeeping is an ephemeral cache, and all durable state lives in workers or on the host.

Processes and restrictions

  • Root supervisor, the gateway's own pattern: installs OUTPUT rules admitting only the adapter endpoints in the committed snapshot, INPUT rules admitting only each member's gateway address on that bridge's interface to the hub port (policy DROP otherwise), disables forwarding, and reloads on signal. Takes no input from the proxy. The INPUT rules are hygiene under strict and the required control under isolate=true.
  • Unprivileged proxy, non-root, no capabilities, read-only rootfs, no-new-privileges, started by the supervisor. Cannot modify the snapshot.
  • No engine socket. Mounts: the snapshot directory read-only, a status directory for the two status files, and the audit log path.
  • Proxy targets are member names resolved from the committed snapshot, never addresses, URLs or commands from a request. The hub is not a general proxy.
  • Blast radius of a compromised proxy: send tasks to and read results from every worker in its group, using the outbound tokens it holds. Nothing else. A compromised supervisor is a root container on each member bridge: it can read every outbound token of its group and, with its own rules removed, reach the host and the internet through the engine's NAT. Member gateways drop all hub-sourced traffic except to the adapter port, ahead of their published-port rules, so it reaches no member listener beyond the adapter. Measured in P1 (CR-P1D-2, prototypes.md).

Revisioned snapshot publication

  • The host publishes a snapshot per revision: a directory named by the revision number under the group's snapshot root, containing the membership file (members, roles, member generations, canonical project paths, mount modes, adapter endpoints, hub addresses, hashes of inbound session-to-hub tokens), the secrets file (outbound hub-to-worker tokens, owned and readable by the proxy uid only), and a manifest listing both files with content hashes and the revision.
  • The group's snapshot root is mounted into the hub as a directory, never individual files, so new snapshot directories become visible without inode pinning. Activation is an atomic rename of a current symlink inside the root.
  • Supervisor and proxy load only through current, verify both files against the manifest hashes, and refuse a snapshot whose files disagree with the manifest or carry different revisions. A reader that observes a mixed or corrupt snapshot keeps its last committed revision and reports the error and the rejected revision in its status file.
  • Each reader writes its applied revision to its own status file. The host treats a publication as committed only when both status files show the new revision within the ack timeout. A SIGHUP or any other signal is a nudge, never an acknowledgment.
  • Readers cache nothing across restart; on start they load current, verify, and write status. Retention of old snapshot directories is bounded; the host removes them after commit of a newer one.
  • Keeping the last committed revision on a bad update is deliberately not relied on for removals: a removal that fails to commit falls back to the engine-level disconnect described in lifecycle, which cuts connectivity regardless of rules.

Responsibilities

Registry
Served from the committed snapshot: each member's card and a group listing. The only user-provided field is the card description, which is data, not identity.
Policy
Roles are exclusive and host-declared: the one orchestrator sends, workers respond. Workers cannot initiate and cannot address each other. A session is a member of exactly one group.
Proxy
Forwards JSON-RPC to the named worker with SSE passthrough and no buffering. Strips any identity-bearing header, authenticates the inbound token against the snapshot hash, and forwards with that worker's outbound token from the secrets file plus the authenticated principal. Bodies and IDs are never rewritten. Responses are read to cache ownership; the cache is advisory and an absent entry means "forward and let the worker decide".
Orchestrator liveness
Holds the authenticated liveness connection from the orchestrator's client; see departure. Worker connections never establish orchestrator liveness.
Delivery errors
When a worker is unreachable, unknown to the snapshot, or its principal is revoked, the hub returns a JSON-RPC delivery error. The hub never emits an A2A task state; outcomes are adapter-authoritative.
Worktree guard
At join, the host compares the new member's host-canonical project path and mount mode with existing members. Two writable members on one path are refused, the orchestrator included; any other overlap warns. Documented v1 limits: bind-mount aliases, nested additional directories, shared git metadata between linked worktrees, and overlap across groups are not detected.
Audit
JSONL, status-only by default: timestamp, principal, target, group, method, task ID, context ID, outcome code, termination status, snapshot revision. Error entries carry codes and reasons, never excerpts of message text, metadata or the provenance line. Content is logged only with explicit --a2a-log=full.

Addressing and transport

Each member reaches the hub as a2a.enclave, resolved by its own gateway's dnsmasq to the hub's static address on that member's bridge. The hub listens on IPv4 on a port outside 80 and 443. Transport is plaintext HTTP in v1, an explicitly accepted risk: traffic and bearer tokens are readable by root on the host and by anything that gains the gateway's or the hub's network namespace. This is not claimed to be equivalent to any confidentiality the gateway provides elsewhere. TLS is deferred; reusing the gateway CA is one option to evaluate against a dedicated A2A CA or pinned identities, and nothing is selected until trust roots, key issuance, rotation, identity and cross-gateway boundaries are specified.

  • Principal = group, member name, role, member generation. Two unique tokens per member and direction, inbound session-to-hub and outbound hub-to-session, issued at join; the inbound token is revoked at leave or departure, the outbound token at worker leave or group stop. Never shared between workers.
  • Hub authorization is a routing check: exclusive roles, owner match from the advisory cache when present.
  • Worker authorization is authoritative. The adapter binds every task and context to group, worker, principal and member generation. A replacement orchestrator has a new generation and cannot resume or read existing contexts by default; explicit inheritance is a later feature.
  • Handles are locators, not authorization. A task handle is worker name, task ID and member generation; a context handle is worker name, context ID, member generation and a random part. Presenting a handle authorizes nothing; the presented credential's principal must match the binding. Handles are independent of the hub epoch, so hub restart invalidates none.
  • Provenance derives from the authenticated principal, never from request content: message metadata plus one fixed-format line prefixed to the prompt text (bracketed header, fixed field order, no prose, then a blank line), because the harness only sees text. A small shipped skill explains the header. Format, settled with the first adapter: [a2a group=<group> from=<member> role=<role> generation=<generation> task=<taskID> context=<contextID>], fields in this order, single spaces, unquoted, no value containing whitespace or ]; from is _host for the host principal; task and context are the worker's raw IDs, not handles.
  • Reconciliation from engine labels and host records is performed by the enclave CLI, never by the hub.

Host principal

  • One stable host principal per group, provisioned at group creation with its own member generation, recorded in the group record and in every snapshot. Its generation changes only with the group generation, so it cannot inherit across group reuse.
  • Every enclave a2a invocation that acts as the host principal receives a short-lived, single-invocation credential issued by the host under the group lock, representing the host principal, valid for a bounded lifetime and revoked when the invocation ends or the lifetime elapses, whichever comes first. The credential's hash is published in the snapshot for the proxy to verify; its removal is a snapshot revision.
  • Adapters bind tasks and contexts created through such a credential to the host principal and its generation, never to the invocation. A later invocation with a fresh credential may query, cancel or retry a detached task because it presents the same principal and generation.
  • The host principal has no liveness. Its tasks run to their deadlines. A blocking host send returns the final message; a detached host send returns a handle and the work continues to its deadline.

8. Gateway changes

  • Hub attachment. Connected to the session bridge at join with a static address and disconnected at leave by the host. Teardown and GC learn to disconnect an enclave-labeled hub endpoint instead of treating it as foreign.
  • Session-local overlay file. Hub address, port and the a2a.enclave record are written to a per-session file in a directory mounted read-only into the gateway and re-read on reload. Not environment variables, which cannot change on a running gateway, and never the per-project bundle, which a reload would clobber for other sessions.
  • INPUT (filter): -i <bridge if> -s <hub address> -p tcp --dport <adapter port> -j ACCEPT.
  • OUTPUT (filter): accept -d <hub address> -p tcp --dport <hub port>.
  • OUTPUT (nat): explicit RETURN for the hub address before the REDIRECT rules, even though the hub port is outside 80 and 443.
  • IPv6 guarantee: adapter and hub listen on IPv4 only, and the existing ip6tables INPUT and OUTPUT DROP policies receive no A2A exception. Link-local addresses exist on every interface; this rule is what makes them irrelevant, not IPAM configuration.
  • Restricted mode only. --peer-group is rejected with --allow-all-network and with the qemu backend.
  • Podman support matrix. strict is the supported configuration and is used whenever netavark offers it. isolate=true is a supported but explicitly weaker fallback, conditional on P1-P, with the difference stated below. Without an isolate option, --peer-group is rejected with a message naming the required netavark version. Decided by CR-1.
CR-1 (accepted 2026-11-05, reviewer concurring with one correction): isolate=true as an explicitly weaker fallback, conditional on P1-P. Astra's review had asked for strict only, accepted the fallback, and objected to a security-equivalence rationale that omitted the published-port exception. That objection is upheld; the fallback is not equivalent.

Measured on Ubuntu 24.04, podman 4.9.3 rootless, netavark 1.4.0 (no strict), two isolate=true bridges, a multi-homed hub, and a bystander on a non-isolated bridge: members cannot reach each other in either direction; the hub reaches each member only over that member's bridge; a member reaches the hub only at the hub's address on its own bridge; routing through the hub is blocked. A non-isolated bystander can reach member bridges and the hub address; that is the only thing strict adds, in both directions.

Inbound bystander traffic to a member is dropped by the gateway INPUT policy except on published ports: the existing rules accept each published port on any interface, so under isolate=true a non-isolated podman network on the same host can reach a session's published listeners (a dev server, the OAuth callback port) directly, bypassing the host's loopback binding. This is pre-existing behavior of the isolate=true fallback and A2A neither adds nor removes it; strict blocks it. Outbound member traffic is governed by the gateway OUTPUT allowlist. Inbound bystander traffic to the hub is closed by hub INPUT rules: the supervisor admits, per bridge interface, only that member's gateway address to the hub port, everything else dropped. With that rule the A2A message plane has the same reachability under both values; the session's published ports do not.

Decision: --peer-group requires a netavark that accepts the isolate option; strict when available, true as a weaker fallback that the existing netavark warning already announces; the hub installs the INPUT rules unconditionally. P1-P must reproduce the matrix under both values and must include a bystander reaching a member's published port under isolate=true, recorded as expected. Scoping the published-port INPUT rules to the engine's forwarding source is a separate hardening outside A2A (see Later). Full data in prototypes.md.

A later hardening step can remove the gateway INPUT rule by having the adapter open an outbound connection to the hub and multiplexing requests back over it. Not in v1.

9. In-container pieces

One Go binary with two modes, baked into the tool image like the other runtime assets.

Server adapter (worker side)

  • Listens on the adapter port on IPv4, serves the agent card, accepts send and stream. Rejects any request lacking this worker's outbound token or carrying a principal of an unknown member generation.
  • Keeps an authenticated control connection to the hub, over which the hub presents its epoch. Used for streaming and for detecting hub loss. It never establishes orchestrator liveness.
  • Turns each message into a headless harness invocation. Each context ID maps to one harness session; follow-up turns use the harness's resume mechanism. Cheap in principle; confirmed by P2.
  • Owns the persisted context table under a fixed subdirectory of the worker's config store on the host: contexts, bindings, harness session IDs, last activity, task records with state and termination, queued task IDs, tombstones, dedupe records, per-principal admission-stop flags, quarantine state. This is the durable record; the hub has none. The host reads it directly from the filesystem for ps and reconcile.
  • Returns the worker's final assistant message only, never the event stream or tool calls. Streams task status and artifact events toward the hub for the UI and audit. Terminal results are retained in the table for later fetch.
  • Tasks are serialized per worker. The harness runs in its own process group; the adapter confirms termination of every descendant before dequeuing the next task. Queue depth is advertised in the card.
  • Cancel leaves the worktree untouched. The orchestrator can ask in the next turn of the same context what state was left.
  • No input-required. A headless run answers and exits. A worker that needs a decision ends its turn with the question; the orchestrator answers with the next message in the same context.
  • The tool's spec.yaml declares the invocation: command template, resume argument, event format. Tools without it cannot run in serve mode and report that clearly.
  • A worker runs in serve mode: the adapter is the session's main process. enclave attach shows its log.

Client (orchestrator side)

  • Exposed to the interactive agent as a stdio MCP server with tools list_peers, send_task, get_task, cancel_task.
  • Holds the authenticated orchestrator liveness connection to the hub for as long as the client process runs.
  • send_task blocks up to a wait bound and returns the final message on a terminal state. When the bound elapses it returns a task handle with the actual current state: submitted with queue position, or working. The task continues; get_task retrieves it. A wait timeout is never a cancellation.
  • Explicit retries only. Each send carries a client message ID. A send is a retry only when flagged as one; the client preserves the message ID and retry flag across its own reconnects. Unflagged sends are new tasks.
  • No streaming tool. Expectation, confirmed by P3 for model-context visibility only: MCP progress notifications do not enter the model context in Claude Code, and a streamed tool result would put the worker's output into the orchestrator's context a second time. P3 makes no claims about billing, caching or token accounting.
  • Wired into the harness by a baked MCP config file that the session launch passes to the harness for orchestrator sessions only (sandbox.a2a.orchestratorArgs); settings templates and patches apply to every session and cannot depend on the role. A plain CLI fallback for tools without MCP.

10. Contexts, handles, dedupe

  • Create versus resume. A send without a context ID creates a context; the worker issues the handle. A send with a context ID must match a live binding on that worker for the same principal and generation. Unknown IDs are rejected; expired IDs answer "expired" from a tombstone; a handle issued by another worker is unknown by construction. The hub never routes by context, since every request names its worker.
  • Dedupe at the worker. Lookup by principal, member generation and client message ID, without needing a context ID. Admission is persisted in the context table before execution starts, and the record binds the message ID to the request content; a reuse with different content is rejected. A flagged retry whose original is known returns its outcome or attaches to it in flight, including after a hub restart, because the record is in the worker. A flagged retry whose original is evicted or from another generation is rejected as ambiguous, never replayed.
  • Epoch independence. Task and context lookups go to the worker by handle; the hub's cache is advisory. A fresh hub forwards queries it has never seen and the worker's binding decides. Absent cache never means allow and never means deny.
  • Tombstones and records are bounded by count and age (see bounds); eviction of a dedupe record turns a later flagged retry into an ambiguous rejection, which is the intended fail-closed result.

12. Task endings and termination status

Outcomes are adapter-authoritative. The hub never emits an A2A terminal state; when it cannot reach the adapter it returns a delivery error and the task keeps the adapter's last reported state. A terminal state never by itself implies the work stopped; the adapter sets a separate termination field, which the hub forwards and never infers.

13. Liveness, departure, acknowledgments, quarantine

  • Liveness source. Only the authenticated orchestrator-to-hub connection held by the client establishes orchestrator liveness. Worker connections prove nothing about the orchestrator. The host principal has no liveness.
  • Prompt detection where a host process exists: a foreground orchestrator's enclave process observes container exit and initiates authoritative departure. Abrupt loss of that enclave process (for example kill -9) removes the observer and falls back to the bounded path.
  • Bounded detection otherwise (background orchestrators, lost observer): liveness connection absent past the reconnect window means suspected departure.
  • On suspected departure, each adapter persists an admission-stop flag for that principal, stops dequeuing for it, fails its queued tasks with reason orchestrator-lost, and lets running work continue only to its existing execution deadline. A later reconnect does not silently undo this: admission resumes only after a host reconcile confirms the orchestrator is alive and its generation unchanged.
  • Authoritative departure is a host-observed session stop or removal. The host revokes the inbound token by snapshot revision (proxy ack closes that principal's streams), then requires from every worker an acknowledgment carrying three facts: the admission-stop flag for that principal is persisted; queued work for that principal is discarded and recorded as failed with reason orchestrator-lost; running work for that principal is terminated, with the termination field set by the adapter.
  • Completion. The departure is reported complete only when every worker has acknowledged with termination confirmed. A worker that cannot be reached, or reports unconfirmed termination, yields a degraded result: the host records a durable reconciliation obligation in the group record, the worker is quarantined, and the departure is never reported as a successful cancellation. Reconcile retries the acknowledgments until all are confirmed.
  • Connectivity fallback. Supervisor and proxy acks prove access revocation only. The engine-level disconnect of the hub attachment cuts connectivity when revocation cannot commit; it satisfies none of the three worker facts.
  • Quarantine. A worker that cannot confirm termination accepts no new tasks, records the quarantine in its context table, is reported in ps, and is released only by a host reconcile that confirms no descendant survives. Revocation, admission stop and quarantine are durable in the worker's table and the group record; they survive hub restart and are never cleared by reconnection.
  • This is a stated v1 limit: an unattended background orchestrator's exit is seen within the reconnect window as a suspicion, and confirmed at the next host lifecycle command or enclave a2a reconcile.

14. Fail-closed semantics

Reconciliation compares member generations and snapshot revisions; anything from an unknown generation or an uncommitted revision is rejected.

LossBehavior
Hub restarts (new epoch)Adapters observe the new epoch on the control handshake and end old-epoch running and queued tasks per the table. Contexts, bindings, dedupe records, task records and handles are generation-bound in workers and remain valid; the fresh hub forwards and workers decide. Authenticated reconnect that preserves tasks across epochs is a later refinement.
Transient transport loss between adapter and hubNot a departure. The task continues unobserved within the reconnect window; an authenticated reconnect to the same epoch resumes reporting. Past the window the adapter kills and records hub-lost.
Orchestrator departure, suspected or authoritativeSee departure.
Terminal detach, MCP client restart, caller wait timeoutNever a cancellation. The task is reachable by its handle; the client's liveness connection is re-established on restart within the window.
Snapshot publication fails to commitFor additions: the join fails and is rolled back. For removals: engine-level disconnect and degraded report; the obligation stays in the group record.
Lost execution state (adapter restart with a surviving subprocess)Resume and replay are rejected; the surviving process group is killed and termination confirmed before any conflicting work starts; the outcome is reported unknown.
Lost context ownership (binding record missing)Resume is refused even when the transcript exists.
Lost or evicted dedupe recordA flagged retry is rejected as ambiguous.
Worker session stoppedRunning task shows a delivery error at the hub; its record in the worker's table is what reconcile reads; contexts follow retention.

15. Lifecycle: join, leave, teardown, recovery

Join (host, under the group lock)

  1. Create or load the group record and group generation; on first creation provision the host principal.
  2. Write the cleanup inventory entry for the new member (store path, member generation, group generation) before anything else, so a crash at any later step leaves something to delete.
  3. Provision principal, member generation and both tokens; run the worktree guard.
  4. Start the hub if absent; assign a static hub address on the session bridge and connect.
  5. Write the session-local gateway overlay and reload the gateway.
  6. Publish snapshot revision N+1 (membership, secrets, manifest), swap current, and wait for supervisor and proxy acks of N+1. No ack within the timeout: roll back every step above, including the inventory entry, and fail the join.
  7. Start the session with its token and adapter configuration.

Leave (host, under the group lock)

  1. Record leave intent in the group record.
  2. Publish a snapshot without the member: inbound token hash removed, and for a worker its outbound token removed. Wait for the proxy ack (streams for that principal closed, token refused) and the supervisor ack (deny rules applied, conntrack entries for the endpoint flushed).
  3. For an orchestrator or host-initiated departure: collect the three-fact worker acknowledgments from every worker (departure).
  4. Disconnect the hub from the member's bridge. If step 2 did not commit, this step runs immediately as the connectivity fallback and the leave is reported degraded.
  5. Remove the gateway overlay; stop the hub if it was the last member.
  6. Mark the inventory entry eligible for deletion at group teardown; retain it until deletion succeeds.
  • Teardown disconnects the hub before removing the session network; the foreign-endpoint rule is amended to recognize enclave-labeled hub endpoints as owned.
  • Reconciliation runs on every session start, stop, cleanup --ephemeral and enclave a2a reconcile: hubs attached to bridges whose session is gone are disconnected; hubs with zero members are removed; stale attachments past the existing grace period are cleaned like stale networks; uncommitted snapshot revisions are re-published or rolled back; pending departure obligations are retried; quarantined workers are checked and released when no descendant survives; suspected departures are confirmed or cleared; pending cleanup inventory entries are retried.
  • Hub lifetime: first member joins to last member's session container removed. A stopped background worker keeps its network and therefore keeps the hub alive.
  • Stopping the orchestrator is authoritative departure for its principal, leaves background workers up, and prints the member list with the stop command. enclave stop --peer-group <name> stops every member and the hub. No interactive prompt in the stop path.

16. Retention, inventory, cleanup

TTL is context expiration, not guaranteed data erasure. Three kinds of state are distinguished:

StateOwnerExpiresErased
Hub cache (owners, retained terminal summaries, streams) and snapshot directoriesHub, in memory per epoch; host for snapshotsRetention bound, hub restart; old snapshots after a newer commitWith the hub; by the host
Context table: bindings, task records, dedupe records, tombstones, admission-stop flags, quarantine state, A2A-owned harness transcriptsWorker adapter, in a fixed subdirectory of the worker's config store on the hostIdle TTL measured by the adapter from last activity, which is updated at enqueue. A context with queued or running tasks never expires. Expiry unbinds, leaves a bounded tombstone, and deletes the transcript as housekeeping. Admission-stop and quarantine records never expire; only host reconcile clears themAt group teardown by the host, from the cleanup inventory
Shared memory, config store, shell historyExisting per-project storesNever by A2AOnly by the existing cleanup command. Shared across all contexts of a worker and across runs; stated as a caveat in the docs
  • Cleanup inventory. A host-written record per group under the state directory lists every member's A2A store path with member and group generation. It is written before admission, retained until deletion of each entry succeeds, survives worker departure, container removal and hub restart, and is scoped to the group generation so a reused group name or store never causes deletion of another generation's data.
  • Group record. Host-written: group generation, host principal, members and generations, current committed snapshot revision, pending departure obligations, host-confirmed departures and releases.

18. Security model

ConcernHandling
AuthenticationTwo unique tokens per member and direction, host-issued at join. Inbound hashes in the membership file; outbound tokens in the proxy-only secrets file; both published per revision. Member generation checked on every request.
IdentityHost-provisioned principal; inbound identity headers stripped; provenance from the authenticated principal only; handles are locators.
AuthorizationGroup membership is topology. Hub checks roles and an advisory cache for routing; the worker's binding of tasks and contexts to principal and generation is authoritative.
ReachabilityNo host listener. No shared segment. One scoped INPUT, one scoped OUTPUT and one NAT exemption per member. IPv6 blocked by existing DROP policies.
Hub compromiseUnprivileged proxy with name-based targets only; root supervisor fed solely by the committed snapshot; hub INPUT limited to member gateway addresses; mixed or corrupt snapshots refused; revocation by revision with conntrack flush; engine disconnect as connectivity fallback; no engine access. AuditStatus-only by default; codes not content; content only with explicit --a2a-log=full.
Worker self-integrityA worker is trusted about itself. Its harness runs as the adapter's user and can read the adapter's tokens and rewrite its own context table, so that table is advisory for the worker's own state. The host never relies on it to protect another member: isolation between members rests on topology, the hub and per-member tokens, none of which a worker can reach.
Prompt injectionSame risk on every transport. Mitigated by provenance from authenticated identity, workers never initiating, and the shipped skill.
SecretsTokens never recorded in session provenance (AffectsSession rules apply). Membership file carries hashes; the secrets file is readable by the proxy uid only; invocation credentials are bounded and single-use.
EgressUnchanged except the hub rule. The allowlist and proxy govern everything else.

19. Herdr and terminal orchestration

Herdr stays the human's control plane; A2A is the agents' control plane.

  • One Herdr pane per session: enclave --peer-group review --role worker --name worker-1. Herdr's idle and done detection keeps working for interactive sessions.
  • The orchestrator runs interactively in its own pane with the MCP client, which doubles as its liveness connection. Worker output streams in the worker panes.
  • Host-side verbs run through engine exec into the hub or workers, the mechanism policy reload already uses. No host listener.
  • Spawning workers from inside a sandbox is a control capability and stays out of the hub.

21. Token cost and when to use it

CostOrchestratorWorker
Protocol framingZero, envelopes never reach a modelZero
MCP tool definitionsA few hundred tokens once per sessionNone
Provenance prefixNoneRoughly 20 to 30 tokens per message
Task text and resultOnce each, like a subagent prompt and reportOnce each
Fresh contextNoneFull harness system prompt per context ID

This is subagent parity minus forking: a worker can never inherit the orchestrator's context prefix, so everything it needs is serialized into the task text. The blocking send, final-message-only result and serialized workers keep the orchestrator's context from growing more than that. These are context-size observations; billing and caching are provider behavior and not claimed here. A2A across enclaves is an isolation and composition tool, not a token saver. It pays off where subagents' sharing is wrong: least privilege per role, different repositories or trust levels, different harnesses or images, long-lived warm workers, per-worker observability, and later cross-host groups. Fan-out of short tasks in one repository stays with subagents and forks.

22. Dependencies

  • Protocol layer: JSON-RPC 2.0, HTTP, SSE. Go standard library.
  • A2A Go SDK: not used. Hand-written subset validated against the pinned spec, in internal/a2a.

  • In-container binary: a second Go entry point, built like the gateway binary and copied into the tool image.
