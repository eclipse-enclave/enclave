# A9 report: Claude driver and spec block

Branch `a2a-a9`, based on `6fdb667` (tip of `a2a`).

## Summary

- `sandbox.a2a` in a tool's `spec.yaml` is parsed by the spec loader, checked
  while it is decoded, and carried on `model.Profile.A2A`. A tool without the
  block gets `tools.RequireA2A` error `tool "<name>" cannot run in serve mode:
  its spec.yaml has no sandbox.a2a block`.
- `internal/a2aagent/driver/claude`: `claude.New(spec, Options)` implements
  `a2aagent.Driver` for `eventFormat: claude-stream-json`: command building
  (new context, resume), version pin check and stream-json decoding per
  CR-P2-2, with transcript paths per CR-P2-3.
- `extensions/tools/claude/spec.yaml` carries the a2a block.

## Where the code lives, and why not all of it is in `internal/tools`

The struct and its validation are defined in `internal/model/a2a.go`.
`internal/tools/a2aspec.go` keeps the interface names as aliases and thin
wrappers (`A2ASpec`, `A2ASkillSpec`, `ValidateA2ASpec`, `ParseVersionRange`,
`ParseVersion`, `ExtractVersion`, `Version`, `VersionRange`,
`SessionIDPlaceholder`, `EventFormatClaudeStreamJSON`) plus `RequireA2A`.

Reason: `model.Profile` cannot import `internal/tools` (tools imports model),
and having `internal/config` import `internal/tools` made `internal/tools` a
gateway proxy build input (`TestGatewayProxyBuildInputsCoverInternalDeps`
failed). That would tie the gateway image hash to tool handler code, the
coupling CR-A2-1 already avoided. `model` is a gateway input already and
holds other validation (`skills_validation.go`). Consumers use `tools.*` as
interfaces.md section 8 says, so the API is unchanged.

Validation runs inside `specA2A.UnmarshalJSON` (`internal/config/spec.go`),
so every parse path rejects a bad block: built-in specs, user specs and
untrusted install candidates. This needed no edit to `spec_loader.go`. The
unmarshaler decodes with `DisallowUnknownFields`, since a custom unmarshaler
escapes the outer `UnmarshalStrict`. Errors carry the spec path and the field,
for example `parse .../spec.yaml: ... sandbox.a2a.eventFormat "jsonl" is not
supported (supported: claude-stream-json)`.

## Spec block schema

```yaml
sandbox:
  a2a:
    command: [claude, -p, --output-format, stream-json, --verbose]
    newSessionArgs: [--session-id, "{sessionId}"]
    resumeArgs: [--resume, "{sessionId}"]
    eventFormat: claude-stream-json
    versionCommand: [claude, --version]
    versions: ">=2.1.306 <3.0.0"
    skills:
      - id: coding
        name: Coding
        description: Reads, edits and tests code in the worker's project and answers with a summary of what it did.
        tags: [code, review, refactor, test]
```

| Field | Required | Meaning |
| --- | --- | --- |
| `command` | yes | Headless argv. The prompt goes to stdin, never argv. |
| `newSessionArgs` | no | Appended for a new context with a UUID the driver picks. Without it the harness picks the ID and reports it in `system/init`. Added to the W0-B struct (additive). |
| `resumeArgs` | yes | Appended to resume a bound harness session. |
| `eventFormat` | yes | Selects the driver. v1 knows only `claude-stream-json`. |
| `versionCommand`, `versions` | together or neither | Version pin, checked by `Driver.CheckVersion`. |
| `skills[]` | no | Agent card skills (`id`, `name`, `description`, `tags`). |

Validation rules (`model.ValidateA2ASpec`):

- `command` must be non-empty, have no blank tokens, and not contain `{sessionId}`.
- `resumeArgs` must be non-empty, have no blank tokens, and contain `{sessionId}` exactly once (whole token or substring, for example `--resume={sessionId}`).
- `newSessionArgs`, when set, follows the same rule as `resumeArgs`.
- `eventFormat` must be set and in `model.A2AEventFormats`.
- `versionCommand` and `versions` must be set together. `versionCommand` has no blank tokens and no placeholder. `versions` is a space-separated AND of `>=`, `>`, `<=`, `<`, `=` followed by an exact `major.minor.patch`. No prerelease, no `~` or `^`.
- `skills`: `id` must be non-blank and unique, `name` and `description` non-blank, tags non-blank.
- Unknown keys inside the block are load errors, like everywhere else in spec.yaml.

Pin choice: the lower bound is the version P2 checked the stream facts
against (2.1.306). The upper bound is the next major. The image installs the
latest Claude Code (`install.sh`), so if a 3.x release ships, serve mode
refuses to start until someone reviews the pin and bumps it. That is
deliberate.

## Driver behavior

`Command(ctx, inv)`:

- argv is `command`, then `Options.ExtraArgs`, then one of:
  - `resumeArgs` with `inv.HarnessSessionID`, which must be a UUID or the call fails (no argv injection from a table value);
  - `newSessionArgs` with a fresh random v4 UUID;
  - nothing, when there is no `newSessionArgs`.
- `Dir` is `inv.WorkDir`.
- `Env` is `inv.Env` (or `os.Environ()` when nil) plus `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` last, so it wins over an inherited value. The executor still strips `ENCLAVE_A2A_*`.
- Uses `exec.Command`, not `CommandContext`: the executor owns killing (CR-P2-1).

`CheckVersion(ctx)` runs `versionCommand`, takes the first
`major.minor.patch` in stdout and checks it against `versions`. It fails on
a non-zero exit, on output without a version, or on a version outside the
range. Without `versionCommand` it does nothing. A10 must not run it while
a task is running (A8 sweep note).

`Decode(r, emit)` reads to EOF (lines up to 64 MiB; longer ones are drained,
logged and skipped). Each event kind decodes only its own fields, so a field
with another shape in a different event (`system/permission_denied` has a
string `message`) cannot break the decode.

| stream-json event | Mapping |
| --- | --- |
| `system/init` | First per distinct `session_id`: `EventSession{HarnessSessionID}`. Records the transcript paths from `cwd` and `session_id`, and marks a turn open. A repeated init for the same session only re-opens the turn (P2 background-task case). Missing `session_id` or a malformed init is a protocol error. |
| `assistant`, main thread (`parent_tool_use_id` null) | `EventProgress{Text}` with the text blocks joined by newlines. Tool use and thinking blocks are never emitted. |
| `assistant`, subagent (`parent_tool_use_id` set) | skipped |
| `result` | Remembered as the latest result and closes the turn. A successful result before any `system/init` is a protocol error. A malformed result is a protocol error. |
| `user`, `rate_limit_event`, `stream_event`, `system/{thinking_tokens, task_started, task_updated, task_notification, task_progress, background_tasks_changed, permission_denied, compact_boundary, status, hook_started, hook_progress, hook_response}` | skipped silently |
| any other type or `system` subtype | skipped, logged once per kind (`Options.Log`) |
| line that is not a JSON object | skipped, logged |

At EOF:

| Condition | Result |
| --- | --- |
| protocol error recorded | that error |
| no `result`, no `system/init` (empty stdout, for example "Session ID already in use") | error `claude stream ended without a result: no system/init` |
| `system/init` seen, no `result` (killed run) | `errNoOutcome` |
| last `result` has `is_error` or a subtype other than `success` (`error_during_execution`, `error_max_turns`, ...) | error with the subtype and the `errors[]` (or `result`) text; unknown resume gives `claude result error_during_execution: No conversation found with session ID: <id>` |
| a `system/init` after the last `result` and no later result | `errNoOutcome: a turn started after the last result` |
| otherwise | `EventFinal{Text: result}` once, then `Outcome{FinalMessage}` |

Every return, error or not, carries `HarnessSessionID` and `Transcripts`
when an init was seen, so the executor binds and later deletes files from
failed and killed runs too.

Transcripts (CR-P2-3) are config-store-relative, for session `<sid>` created
in `<cwd>`:

- `projects/<enc>/<sid>.jsonl` and `projects/<enc>/<sid>/` (subagent transcripts and tool-result spill)
- `session-env/<sid>/`, `file-history/<sid>/`, `tasks/<sid>/`

`<enc>` is the cwd with every character outside `[A-Za-z0-9]` replaced by
`-`; a non-BMP rune becomes two dashes, because Claude replaces UTF-16 code
units. Checked against the host's `~/.claude/projects` names
(`.local` becomes `--local`). Claude shortens names over 200 characters with
a hash this driver does not reproduce. For such a cwd only the three
non-project paths are reported, and the driver logs it. `TranscriptPaths`
is exported for A2 or A13 if they need the same list.

CR-P2-3 expected a new `Driver` method. None is needed:
`Outcome.Transcripts` already carries the list and the executor already
passes it to `BindHarnessSession` (see CR-A9-2 for the timing gap).

## Change requests

- **CR-A9-1** (section 8 `Invocation`/`Executor`, P2, CR-P2-2). CR-P2-2 asks
  for the new session ID to be "chosen and persisted before spawn". The
  interface cannot do that: `Command` returns only an `*exec.Cmd`, and the
  executor binds the ID only when it sees `EventSession`. Today the driver
  picks the UUID inside `Command`, and the ID reaches the table with
  `system/init`, 0.26 to 0.66 s after spawn (P2). A crash in that window loses
  an ID whose files Claude has probably not written yet.
  Proposal: add `Driver.NewSessionID() (string, error)` (empty when the spec
  has no `newSessionArgs`) and `Invocation.NewHarnessSessionID`. The executor
  calls `NewSessionID`, persists it with `BindHarnessSession` before `Start`,
  and passes it in; the driver then uses it instead of generating one.
  Affects `driver.go` (W0-B) and the executor (A8). Not implemented.
- **CR-A9-2** (section 8 `HarnessEvent`, executor). The executor binds
  `Outcome.Transcripts` only after `Decode` returns. If the adapter crashes
  mid-run, the context record has the session ID (bound at init) but no
  transcript paths, so inventory deletion misses them.
  Proposal: add `Transcripts []string` to `HarnessEvent`, filled on
  `EventSession`, which the executor passes to `BindHarnessSession`. The
  driver already has the paths at init. Low priority. Not implemented.

## Open items

For D5 (docs):

- Document `sandbox.a2a` (table and rules above) in
  `docs/extensions/README.md` and `docs/extensions/adding-a-tool.md`, and
  state that a tool without it cannot run in serve mode.
- Note the version pin and that a Claude Code major release blocks serve
  mode until the pin is bumped.

For A10, A14 and the coordinator:

- **Permissions.** Headless `claude -p` runs in `dontAsk` mode (the P2
  fixture shows `permissionMode: "dontAsk"` and a `system/permission_denied`
  for Bash). A worker without a permission flag cannot edit or run tools.
  The spec command does not include the yolo flag, because yolo is a
  per-session option. A10 (or A14) should pass `Profile.YoloFlag` through
  `claude.Options.ExtraArgs` when the session runs with yolo, and decide what
  a non-yolo worker gets (for example `--permission-mode acceptEdits`).
- **Empty replies fail.** The executor treats a run as successful only when
  `FinalMessage != ""` (A8). A successful turn with empty text therefore
  fails.
- **Resume from another directory.** The transcript stays in the creating
  cwd's project directory. The executor's `WorkDir` is fixed per worker, so
  the derived paths stay correct. If that ever changes, store the creating
  cwd.
- The spec summary (`spec_summary.go`, `enclave tools list`) does not show
  whether a tool supports serve mode. A13 or D5 may want a capability row.

For I2:

- Whether `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` also stops background
  subagents (from P2).
- The billed integration test (`TestRealNewContextAndResume`: new context,
  check the derived transcript file exists, resume and get the same session
  ID) has not been run. No `ANTHROPIC_API_KEY` or `CLAUDE_CODE_OAUTH_TOKEN`
  was available, and the test must not use the user's Claude config.
