# P3: client prototype report

Date: 2026-11-05. Host: Linux 6.17, Claude Code 2.1.306, model `haiku`
(claude-haiku-5-5) for all runs. Base: `a2a` at 33158d4.

Exit criterion: evidence list 23.P3; wait default, credential lifetime
measured. Met, with two findings that change the proposal: the 10 min send
wait placeholder does not work in interactive Claude Code, and retry identity
across a client process restart needs a client-side journal.

## Setup

Throwaway code under `/tmp/a2a-p3/` (not committed):

- `src/main.go`: one Go binary, standard library only. `mcp` is a stdio MCP
  server with a hand-written JSON-RPC handshake and the four tools
  `list_peers`, `send_task`, `get_task`, `cancel_task`. The fake hub and
  worker run in process and keep their state in a flock-guarded JSON file,
  which stands in for the worker's context table so that it survives client
  restarts. Task progress is computed from wall-clock schedule (serial
  worker, queue). The binary emits `notifications/progress` (with the
  `progressToken` Claude Code sends) and `notifications/message` carrying
  canary strings. `drive` is a scripted MCP client covering the protocol
  scenarios without a model. `host` simulates the host-principal
  invocation credentials.
- `run.sh`: one `claude -p` run with `--strict-mcp-config --mcp-config
  <file in /tmp> --tools '' --setting-sources '' --no-session-persistence
  --output-format stream-json --verbose`. User settings were not touched.
- `interactive.sh`: one interactive TUI run in a pty (`script`), prompt typed
  after MCP connect.
- `claude-strings.txt`: `strings` of the Claude Code binary, used to read
  the timeout code paths and defaults.

Real Claude invocations: 12 (11 `-p`, 1 interactive after a first
interactive attempt raced the non-blocking MCP connect). Total cost under
USD 0.01.

## Failed or partial items first

| Item | Result |
| --- | --- |
| Wait timeout returning a handle, with the 10 min placeholder | **Fails in interactive Claude Code.** At 120 s Claude Code moves any MCP call to the background (default on, observed in r7). The model gets Claude's background task ID instead of our handle, and in both runs (r5, r7) it passed that ID to `get_task` as a handle. The handle only arrives with the completion notification. A send wait below 120 s fixes this; see the recommendation. |
| Retry identity across client process restart | **Fails as designed.** When the stdio server dies mid-call the model sees only `Connection closed` (r6). It never received a message ID or handle, so it cannot flag a retry. Claude Code restarts the server on the next call without telling the model. The task kept running on the worker. Needs a client journal (A11 facts 5 and 6). The proposal's "preserves the message ID and retry flag across its own reconnects" covers hub reconnects only. |
| Client-side limits set lower by the user | A hard tool timeout (`MCP_TOOL_TIMEOUT`) or idle timeout below the send wait aborts the call with no handle (r2, r3). The client cannot see these values for certain. Same journal fix; A15 should not set them. |
| Flagged retry after hub restart, after eviction, foreign generation | Fake-hub simulation only. The logic holds in the fake, but the real behavior lives in the adapter. **Deferred** to A10 (dedupe, bindings), A11 (client) tests and I2. |
| Host-principal detached send, get, cancel, retry | Fake-hub simulation only. Credential issuance by snapshot revision is not measurable without P1's hub. **Deferred** to A13 and I2; commit latency is P1's. |

## Claude Code client limits (2.1.306)

Read from the binary, then confirmed live where marked.

| Limit | Default | Override | On hit | Live |
| --- | --- | --- | --- | --- |
| Hard tool-call timeout | 1e8 ms (27.8 h); progress does not extend it | `MCP_TOOL_TIMEOUT` env (ms); per-server `timeout` (ms, at least 1000) in the `mcpServers` entry wins over the env | Sends `notifications/cancelled` (`reason: "SdkError: Request timed out"`). Model sees `MCP server "a2a" tool "send_task" timed out after 60s`. | r2 (60000) |
| Idle timeout (no response or progress) | stdio 30 min, http/sse 5 min, checked every 30 s | `CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT` (ms, 0 disables); a per-server `timeout` raises the floor; capped at the hard timeout | No `notifications/cancelled` is sent, so the server keeps waiting. Model sees `… sent no response or progress for 60s; aborting. …` | r3 (45000, silent: aborted at 60 s); r3b (45000, progress every 10 s: survived 150 s) |
| Auto-background | 120 s in interactive sessions, behind feature flag `tengu_mcp_auto_background` (default on). Off in `-p` unless `CLAUDE_AUTO_BACKGROUND_TASKS` is set. Not applied inside subagents. | `CLAUDE_CODE_MCP_AUTO_BACKGROUND_MS` (0 disables) | Model gets `MCP tool "a2a/send_task" is still running after 120s. It was moved to the background as task <id> and keeps running; you'll receive a notification … To stop it, use TaskStop … Note: it does not survive exiting this session.` The result later arrives as a `<task-notification>`. In `-p`, the session ended and the call was dropped without `notifications/cancelled` (r5). | r7 (default 120 s), r5 (20000) |

So there is no blocking limit short of 27.8 h in `-p`. The binding limit for
interactive orchestrators is auto-background at 120 s.

## Recommendation: send wait default

- **`a2a_send_wait` (MCP): 90 s.** That is under the 120 s auto-background
  with room for the progress-poll granularity and response latency, and far
  under the 30 min idle and 27.8 h hard limits. Clamp the model's
  `wait_seconds` to it. Apply the same bound to a blocking `get_task`.
- Rejected alternative: keep 10 min and rely on auto-background. The model
  holds no handle while the call is backgrounded and mistook Claude's task
  ID for one twice. The result is also lost if the session exits.
- Rejected alternative: set `CLAUDE_CODE_MCP_AUTO_BACKGROUND_MS=0` in the
  orchestrator env. That pins the orchestrator's turn for the whole wait.
  It also depends on a remotely flagged feature whose default may change.
- Cost of 90 s: a long task costs one `get_task` turn per 90 s, roughly 100
  tokens of result each. The model can do other work between polls. Record
  this as the 21 trade-off.
- Send `notifications/progress` at most every 30 s whenever a progress token
  is present. It costs no model context, keeps the idle timer satisfied if a
  user raises the wait, and shows the user the worker state in the TUI.
- **Host blocking send (`enclave a2a send`): keep 10 min.** No Claude Code
  limit applies on the host path. This splits the bounds row "Blocking send
  wait (MCP and host)" into two values. The `ENCLAVE_A2A_SEND_WAIT` env
  (interfaces 6) is orchestrator only, so it carries the MCP value. The host
  value needs its own option or a `--wait` flag (A12/A13).

## Recommendation: host invocation credential lifetime

Measured in the fake: credential issue and revoke are file writes under a
lock (40 to 160 µs). The real cost is two snapshot revisions per invocation
(publish the hash, remove it), each bounded by the 10 s commit ack timeout.
That is P1's number and not measurable here.

Reasoning: the normal path revokes at invocation end, so the lifetime only
bounds how long a credential stays valid after the CLI is killed (`kill -9`,
lost terminal). It must also outlive the operation, because expiry
mid-stream closes the stream (H6; the task continues, but the CLI loses its
wait).

- Per invocation: **lifetime = operation bound + 60 s**, issued by the host
  under the group lock.
- Non-blocking verbs (`send --detach`, `task get|cancel|retry`): **2 min**.
  This covers two commit timeouts and the call.
- Blocking `send`: **host send wait + 60 s**, so 11 min at the 10 min
  default.
- Keep **15 min** as the cap (`a2a_credential_lifetime`), and reject a host
  `--wait` above cap minus 60 s.
- If a credential still expires mid-wait, the CLI already holds the task ID
  from the first `SendStreamingMessage` event. It prints the handle and exits
  4, the same as a wait timeout.

## MCP tool shape facts for A11 (and A15)

1. Handshake: Claude Code first sends `server/discover` (id
   `server-discover-probe-1`, `_meta` protocolVersion `2026-07-28`).
   Answering `-32601` makes it fall back to `initialize` with
   `protocolVersion: "2025-11-25"`. Echoing that version worked. Client
   capabilities: `roots`, `elicitation`.
2. Every `tools/call` carries `_meta.progressToken` (an integer) and
   `_meta["claudecode/toolUseId"]`.
3. The model sees the result `content` text verbatim. With `isError: true`
   it treats the text as an error. A JSON object in the text worked: Haiku
   extracted `handle` and reused it correctly (r4).
4. MCP cancellation (`notifications/cancelled`) arrives only on the hard
   timeout. Idle abort, session exit and background stop just drop the
   call or close stdin. A11 must treat every one of these as "stop waiting":
   drop the stream, never `CancelTask`. Only `cancel_task` cancels.
5. Crash or restart of the client process: Claude Code respawns the stdio
   server on the next call. The lost call's only trace in context is
   `Connection closed`. A11 therefore needs a durable send journal in the
   orchestrator container, written before the request goes out: message
   ID, peer, context, content hash, and the task handle once the first
   stream event arrives.
6. Proposed tool shape. A flagged retry stays explicit:
   `send_task {peer, text, context?, wait_seconds?, retry?, message_id?}`.
   With `retry: true` and no `message_id`, the client resolves the unique
   journal entry with the same peer, text and context, or errors and lists
   the candidates. Lost handles must be recoverable: `get_task` without a
   handle returns this principal's recent journal entries (handle, peer,
   state, message ID). Neither adds a tool, so this is a change to
   interfaces 8 only by description. A11 should record it as a CR.
7. Result fields that worked: `handle`, `state` (A2A enum name), `queuePosition`
   (while submitted), `messageId`, `context`, `reason` and `termination`
   (terminal failures), `message` (final text), and `note` (wait elapsed,
   not canceled). The tool description must say that the handle is the
   `task:` value and not a Claude Code task ID. `get_task` should answer a
   non-`task:` argument with that hint.
8. Tool definitions cost: 4,184 vs 3,163 input tokens for a one-word reply
   with and without the server (r0 vs baseline), so about 1,000 tokens for
   these four verbose descriptions. Proposal 21 says "a few hundred". Trim
   the descriptions to meet it.
9. A15 can set a per-server `timeout` (ms) in the `mcpServers` entry; it
   raises both the hard and the idle floor for this server only. Leave it
   unset at a 90 s wait. The auto-background threshold is harness env
   (`CLAUDE_CODE_MCP_AUTO_BACKGROUND_MS`), not server config.
10. Calls made inside Claude subagents are never auto-backgrounded. The
    90 s wait is safe there too.

## Proposal and interfaces changes suggested

- Proposal 17: split "Blocking send wait (MCP and host)" into MCP 90 s
  (decided, P3) and host 10 min. Credential lifetime becomes "operation
  bound + 60 s, cap 15 min, or invocation end".
- Proposal 9 client: add the send journal, journal-resolved flagged retry
  and handle recovery (facts 5 and 6). Replace "No streaming tool.
  Expectation, confirmed by P3" with the measured result, including the
  auto-background notification path.
- Proposal 14 "MCP client restart": a restart loses the in-flight result in
  the model's view. Recovery is through the journal, not through the model.

message with a timestamp), and `out.jsonl` (stream-json) or `tty.log`.
