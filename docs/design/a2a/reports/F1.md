## Decisions inside the contract

- **Session ID before spawn.** `Driver.NewSessionID()` returns empty when
  the spec has no `newSessionArgs`. The executor binds a non-empty ID with
  `BindHarnessSession` before `Start` and passes it as
  `Invocation.NewHarnessSessionID`; the Claude driver now refuses a new
  context without a valid one. If a run ends before the harness reported
  the session (crash before `system/init`), the next turn in that context
  creates the same ID again instead of resuming a session that may not
  exist. That memory is in-process only; after an adapter restart such a
  context resumes and fails if Claude never created the session, which is
  the narrow case CR-A9-1 accepted.
- **Empty reply.** A run that exits 0 with a decoded outcome completes even
  when `FinalMessage` is empty. A completed task always has the `result`
  artifact with one text part (empty here), on the stream and in `GetTask`.
- **Truncation.** The marker is `"\n\n[enclave: result truncated]"` and
  counts toward `ENCLAVE_A2A_MAX_RESULT_BYTES`, so the stored result and the
  artifact stay within the bound. `truncated: true` rides with
  `termination` on `Task.metadata` and the terminal status event.
- **Membership.** `principals` lists all members sorted by name, then
  `_host` with role `host`. The liveness stream's `hello` carries the same
  list (it shares `startStream`). The hub subscribes a control stream to
  revisions before writing `hello`, then sends one `membership` right after
  the orchestrator state if a revision was applied in between, so none is
  missed. A revoked control stream is closed rather than sent the event.
- **Adapter membership check.** After the existing group and role checks,
  the principal (member, role, generation) must be in the newest
  membership. Because the `membership` event and a request forwarded under
  the new revision race, a request whose `X-Enclave-A2A-Revision` is newer
  than the held membership waits up to the epoch wait (30 s). A request
  before any `hello` gets `-31019` after that wait; this also applies to
  `GetTask`, `CancelTask` and `SubscribeToTask`, which previously answered
  without a control connection. Every `hello` replaces the membership; a
  `membership` event older than the held one is ignored. The orchestrator
  "superseded generation" check from A10 stays as a second guard.
- **Yolo.** The `sandbox.a2a` block has no yolo field and the profile's
  `sandbox.yoloFlag` is not visible inside the container, so
  `ENCLAVE_A2A_HARNESS` carries it as an extra `"yoloFlag"` member next to
  the block (decoded with unknown fields still refused). With
  `ENCLAVE_YOLO=1` and a non-empty flag the adapter appends it to the
  driver's extra args; otherwise it logs that the worker runs without
  bypassed permissions and continues (I1 rejects a non-yolo worker earlier).
  `a2a.EnvYolo` mirrors `model.EnvYolo` because the agent does not import
  `internal/model`.
- **Reasons.** The context table's refusal reasons now alias the
  `a2a.Refusal*` constants, so every reason the hub or adapter emits is
  defined in `internal/a2a`. The `contexttable.Reason*` names remain.

  nothing was admitted and the send can be repeated unchanged *without*

  Accepted and implemented in F1b (below).

  the same way (resend without the retry flag), and `get`/`cancel` may now
  see `-31019` during the first seconds after an adapter or hub restart.

## F1b: client handling of `-31019` (CR-F1-2)

Branch `a2a-f1b`, based on `ef15c5e` (`a2a` after the F1 merge). Files:
`internal/a2aagent/mcp/client.go` and its tests (the fake hub gains an
`unconfirmed` knob per method). `cmd/enclave-a2a-agent/client.go` needed no
change: `client send|get|cancel` go through the same `mcp.Client`, and the
unconfirmed result exits 1.

- **Send** (`send_task`, `client send`): a `-31019` before the task ID
  resends the identical message (same message ID; the retry flag stays as
  the caller set it, so a plain send is never turned into a flagged retry)
  after a 500 ms backoff, as long as the backoff fits in the remaining send
  wait. Each attempt follows with only the remaining wait. When the wait
  runs out the result is an error without a handle, with the message ID and
  a note that nothing was admitted and the send can be repeated unchanged
  without `retry`. The journal entry is written once before the first
  attempt (`attempts` counts tool calls, not resends) and only records the
  error, so it never carries a handle or state for an unadmitted send.
- **Get and cancel**: `GetTask` resends within the clamped wait (a zero
  wait makes one attempt), `CancelTask` within the send wait. A remaining
  `-31019` is returned with the handle and a "try again shortly" note.
- **Waiting on a task**: a `-31019` on `SubscribeToTask` (the task exists,
  the worker restarted its control connection) counts like a dropped
  stream: the client resubscribes after the usual reopen backoff until the
  wait ends.
