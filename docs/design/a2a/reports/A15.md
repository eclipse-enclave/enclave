## Why the template mechanism alone cannot do it

- Claude Code reads MCP server definitions from `~/.claude.json`,
  `.mcp.json`, `managed-mcp.json`, plugins and `--mcp-config`, not from
  `settings.json`. The settings template therefore cannot carry the server.
- Settings templates are not rendered. The entrypoint copies
  `$ENCLAVE_TOOL_SETTINGS_TEMPLATE` verbatim, and only when the target does
  not exist yet. The target lives in the persistent config store, so it
  cannot depend on the session's role either.
- Extension patches are host files the user writes and are applied for
  every session. They have no role condition.
- `managed-mcp.json` takes exclusive control of MCP servers, which would
  remove the user's own servers.

The condition therefore has to be evaluated at container start, with
`ENCLAVE_A2A_ROLE` in hand. The only role-aware code that runs there is
the A14 wrapper (tool-agnostic) and the tool's `entrypoint.d/setup.sh`.
Both are outside my ownership.

## CR-A15-1: activate the template for orchestrators

2026-11-05, A15, proposal 9 ("wired via the existing config template and
patch mechanism") and P15 "Start the session". Needs an edit to
`extensions/tools/claude/entrypoint.d/setup.sh`.

The entrypoint sources `entrypoint.d/*.sh` at top level, before
`exec "$@"`, so a sourced script can extend the command. Proposed block, at
the end of `setup.sh`:

```sh
# A2A orchestrators get the enclave-a2a MCP server; workers and other sessions do not.
if [ "${ENCLAVE_A2A_ROLE:-}" = "orchestrator" ] && [ "$(basename -- "${1:-}")" = "claude" ]; then
    set -- "$@" --mcp-config /usr/local/share/enclave/templates/claude-a2a-mcp.json
fi
```

- I checked it in a scratch bash script: orchestrator plus `claude` gets
  the flag appended. A worker, an unset role, and a non-claude command
  (`bash`) are unchanged.
- The flag is appended, not inserted after `claude`. `--mcp-config` is
  variadic and would otherwise swallow a following positional prompt.
- `--mcp-config` adds to the user's servers (no `--strict-mcp-config`).
- It writes nothing to `~/.claude.json` and nothing to the config store,
  so a later non-A2A session on the same store sees no residue. That is why
  I prefer it over `claude mcp add -s local`, which would also need the
  playwright-style cleanup.
- Workers run `enclave-a2a-agent serve` (A14 wrapper), so `$1` is never
  `claude` for them and the server can never appear.
- A test for the block belongs in the existing setup.sh tests, if any, or in
  I1/I2.

Alternative, if the coordinator prefers declarative wiring: a spec field
`sandbox.a2a.orchestratorArgs: [--mcp-config, <inline JSON>]`, appended by
the runtime for `--role orchestrator`. It follows the `noMemoryArgs`
pattern and makes the template file unnecessary. It needs spec.yaml, A9's
spec parsing and a runtime change, so it is larger.

Proposal 9 wording: "via the existing config template and patch mechanism"
is inaccurate for Claude. Suggested text: "wired by a baked MCP config
template that the tool's entrypoint passes to the harness for orchestrator
sessions only".

## CR-A15-2: the skill is composed into every Claude session

2026-11-05, A15, proposal 18 and P20 (non-A2A sessions unchanged).
Tool-extension skills (`extensions/tools/<tool>/skills/`) are merged into
the read-only skills mount for every session (`internal/runtime/skills_mount.go`,
`addSkillMounts` and `applyExtensionSkillsLayer`). There is no role or
peer-group filter. As shipped here, `a2a-provenance` is therefore listed in
non-A2A Claude sessions too: one skill description in context, about 50
tokens. Its description scopes it to A2A, so a model should not load it
otherwise, but the session does change. Options:

1. Accept: a single description line.
2. Skip extension skills named `a2a-*` in both functions unless the session
   has `--peer-group` (small Go change in `internal/runtime`, I1 or A9).
3. Move the skill to the A2A image variant (A14) and copy it in from the
   wrapper. That does not work as is: the skills mount is read-only.

I recommend option 2. Also note: every file under `extensions/tools/claude/`
is part of the regular image hash (`hashMergedExtensionFiles`), so this
package rebuilds regular Claude images once. Their behavior is unchanged,
apart from the skill line above.

## Provenance line (final)

Recorded in interfaces.md section 11. The format is unchanged from the
provisional one and is already implemented by A10 (`a2a.ProvenanceFormat`,
`executor.prompt`):

```text
[a2a group=<group> from=<member> role=<role> generation=<generation> task=<taskID> context=<contextID>]

<message text parts joined with \n>
```

- The header line is followed by `\n\n`. Fields are in that fixed order,
  separated by single spaces, unquoted. There is no prose.
- `group`: the group name (`^[a-z0-9][a-z0-9-]{0,31}$`).
- `from`: the sender's member name; `_host` for the host principal.
- `role`: `orchestrator` or `host` (workers never send).
- `generation`: the sender's member generation, 16 lowercase hex
  characters.
- `task`, `context`: the worker's raw task and context IDs, 32 hex
  characters. They are not `task:`/`ctx:` handles.
- Values come only from the authenticated principal and the adapter. None
  contains whitespace or `]`.
- Only the first line of the prompt is the header.
