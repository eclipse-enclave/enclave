# I2 report: smoke and integration

Branch `a2a-i2`, based on `a2a` at `1e0d96f`.

## Summary

The host's Claude login was available inside sessions, so every real-harness
item ran against real Claude Code (model `haiku` through `ANTHROPIC_MODEL`).

The exit criterion holds on Docker and on rootless Podman, with two
exceptions caused by product bugs: `task get` and `task cancel` fail on the
client side (B1), and `enclave a2a reconcile` does not release a quarantine
that did not come from a departure (B3). The cancel itself works on the
worker. Orchestrator plus two workers, send, cancel, orchestrator stop with
acknowledgments, the degraded path with a quarantined worker, reconcile and
teardown with inventory deletion all ran on both engines.

The most serious finding is B2: a reconcile that runs against the wrong
engine tears down a live group of the other engine and deletes its workers'
context tables while they run. Every `--peer-group` start and every `stop`
reconciles all groups, so mixing engines on one host triggers it without
any explicit reconcile.

New files:

- `scripts/a2a-smoke.sh`: the live smoke test (`ENGINE=docker|podman`,
  optional step list, `A2A_SMOKE_REAL=0` skips the four real Claude tasks).
- `internal/a2ae2e/a2a_e2e_docker_test.go` (`//go:build docker && linux`)
  and `doc_test.go`: an end-to-end test of the binary with temporary XDG
  roots and no credentials, so it never bills. The worker's harness fails
  the task for lack of a login, which still covers the route through hub and
  adapter.

## Bugs

Ordered by severity. None is fixed here.

### B1 (high): `task get`, `task cancel` and MCP `get_task`/`cancel_task` always fail

`GetTask` and `CancelTask` return a bare `Task` (spec pin, and
`internal/a2aagent/server/rpc.go` `getTask`/`cancelTask`; the hub's
`internal/a2ahub/observe.go` decodes them that way). Both clients decode
every response with `a2a.DecodeResult`, which expects the
`StreamResponse` wrapper (`{"task": {...}}`).

```text
$ enclave a2a task get --peer-group a2a-i2-d --json task:a2a-i2-w1:072aebb1139f162d:0fb8c93b00e503514a8fef0bb4ddf6c2
{ "schemaVersion": "1", "kind": "a2a-task", "group": "a2a-i2-d",
  "error": "a2a: decode result: want exactly one of task, message, statusUpdate, artifactUpdate, got 0" }
exit 1
```

MCP: `get_task` and `cancel_task` return `{"error":"hub unreachable: a2a:
decode result: ... got 0"}`. The cancel reaches the worker and completes
(task `CANCELED`, termination `confirmed`, audit outcome recorded); only the
client reports an error and exits 1. The `follow` fallback after `-32004`
(`a2a_host.go:529`) has the same problem.

Repro: any host or MCP `get`/`cancel` of a task the worker knows.
Fix: `internal/app/a2a_host.go` (`decodeA2AResponse` or `callOnce`) and
`internal/a2aagent/mcp/hub.go` (`decodeResponse`/`callOnce`): for
`GetTask` and `CancelTask` unmarshal the result into `a2a.Task` and wrap it
as `a2a.Result{Task: &t}`. The unit tests use fakes that answer with the
wrapper; one fake should reuse the server's real encoding.

### B2 (high): reconcile with the other engine tears down a live group

The group record does not name its engine. Host verbs and lifecycle commands
use the configured backend (`docker` on this host). Against a Podman group:

```text
$ enclave a2a send --peer-group a2a-i2-p --json a2a-i2-pw1 "..."
error: the A2A hub of peer group a2a-i2-p is not running; run `enclave a2a reconcile`
$ enclave a2a reconcile --peer-group a2a-i2-p
a2a-i2-p: removed member a2a-i2-pw1: session container is gone
a2a-i2-p: removed member a2a-i2-pw2: session container is gone
a2a-i2-p: tore down the group
exit 0
```

Afterwards the group record and inventory were gone, both workers' `a2a/`
context tables on the host were deleted while the Podman workers and hub
kept running, and `enclave stop --backend podman --peer-group a2a-i2-p`
answered `peer group a2a-i2-p does not exist`. Recovery needed
`a2a reconcile --backend podman` (removed the orphan hub) and two
`stop --name`. Because `ReconcileAll` runs on every `--peer-group` start and
on `stop`/`cleanup`, any Docker command of that kind does the same to every
Podman group (and the reverse).

Fix: record the engine in `group.json` (`internal/peergroup/record.go`, set
on creation in `internal/backend/docker/a2a_join.go`); `ReconcileAll` and
`Reconcile` (`internal/backend/docker/a2a_reconcile.go`) skip or refuse a
group of another engine; `internal/app/a2a_cmd.go` selects the engine from
the record instead of the configured backend.

### B3 (medium): reconcile never releases a quarantine that has no obligation

Only the leave path records a `quarantine-release` obligation. A quarantine
from a cancel, a deadline, `hub-lost` or an epoch change stays forever.

```text
# w2 runs with a2a_termination_timeout=1us; host cancel of its running task
$ enclave a2a peers --peer-group a2a-i2-d
a2a-i2-w2  worker  active  yes  yes  no  quarantine-prone worker
$ enclave a2a send --peer-group a2a-i2-d --json a2a-i2-w2 "Reply ok."
"error": "worker quarantined [-31015 QUARANTINED]"
$ enclave a2a reconcile --peer-group a2a-i2-d
a2a-i2-d: nothing to do
```

`ps --json` keeps `quarantine: "yes"`. Proposal 13 and 15 say reconcile
checks quarantined workers and releases them when no descendant survives.
Fix: in `Reconcile`, read each active worker's `restrictions.json` (as
`hasSuspectedStop` does) and run `retryQuarantineRelease` for a non-null
`quarantine`.

### B4 (medium): an exited orchestrator container is never a departure

`reconcileMembers` treats a member as gone only when its container does not
exist. A background orchestrator that was killed (`docker kill`), crashed,
or whose Claude exited (`enclave continue` without a conversation exits 1)
leaves an exited container. The workers record a suspected departure after
the reconnect window (60 s measured), but reconcile prints `nothing to do`,
the member stays `active`, and the suspicion is never confirmed. Starting a
session with the same name removes the container and the next reconcile
finishes the departure. Fix: in `reconcileMembers`
(`a2a_reconcile.go`), treat `Exists && !Running` as gone for orchestrators
(authoritative departure); for workers keep the documented "a stopped
background worker keeps the hub alive" unless that is reconsidered.

### B5 (medium): signals to a foreground worker's enclave process are swallowed

A foreground worker runs without a TTY. `kill -TERM` or `kill -INT` of the
enclave process does nothing for at least 300 s; the session never leaves.
A terminal Ctrl-C works because the kernel signals the whole process group,
including `docker run`/`podman run`, which then leave cleanly (2.2 s Docker,
2.7 s Podman, member removed, exit 0). Supervisors that signal only the
enclave pid leave the worker running.

```text
$ scripts/a2a-smoke.sh foreground_signal   (both engines)
FAIL: SIGTERM to the enclave process of a foreground worker did not end the session within 15 s
```

Fix: `internal/docker/run.go` `RunWithIOAndStartHook` passes a nil child
channel to `runCommandWithStartHook`, so `relayInterrupts` never runs for
the non-TTY path; relay as `RunInteractiveWithStartHook` does.

### B6 (medium, tests): `make test` fails on the `a2a` tip since 12:15 UTC today

`TestCallThroughProxyAsHost` and `TestHostCredentialForwardsHostPrincipal`
(`internal/a2ahub`) fail with `-31003 revoked principal`. The fixture clock
is fixed at `2026-11-05T12:00:00Z` (`harness_test.go:63`) and host
credentials expire minutes later, but `proxy.go:354` sets the stream
deadline with `context.WithDeadlineCause(ctx, cred.expiresAt, ...)`, which
uses the real clock. Fix: derive the deadline from `Config.Now`
(`time.Now().Add(cred.expiresAt.Sub(cfg.Now()))`), or let the fixture start
at `time.Now()`.

### B7 (low): a frozen orchestrator is not detected

`docker pause` of the orchestrator: the hub's liveness connection stayed
established for more than 200 s and no suspicion was recorded. The hub's
peer is the orchestrator's gateway proxy, and a frozen container's kernel
keeps acknowledging data, so `TCP_USER_TIMEOUT` never fires. Silent loss
between gateway and hub is detected (below). Fix: an application-level
heartbeat from the client on the liveness stream with a hub read deadline
(`internal/a2aagent/mcp/liveness.go`, the hub's liveness handler).

### B8 (low): orchestrator stop exits 3 after its own reconcile resolved everything

In the degraded path the leave reports the unconfirmed termination, then the
post-stop reconcile releases the quarantine and completes the departure in
the same command (no obligation left), yet the exit status is 3.
`a2aLeaver.reconcile` returns `... || l.degraded` (`internal/app/a2a_wiring.go`).
Either recompute from the record after the reconcile or document that 3
means "was degraded".

### B9 (low): host verbs ignore the handle's worker generation

`enclave a2a task get` with the generation in the handle replaced by
`0000000000000000` reached the worker (audit: `GetTask`, outcome 0). The
MCP client refuses foreign generations; the host client does not. Task IDs
are random per generation, so this fails closed in practice. Fix: compare
the handle generation with the current membership in `a2a_host.go`.

### B10 (low): the proxy keeps a stale rejection in its status

After a corrupt revision was refused and the previous revision re-applied,
the supervisor cleared `rejectedRevision`; the proxy kept
`rejectedRevision: 5` and the error. A later legitimate revision 5 (I reused
the number with a hand-made snapshot) was then reported as refused from the
stale status and the host commit failed. Only revision number reuse reaches
this; the stale status is still misleading. Location: the proxy's status
write on apply (`internal/a2ahub`).

### B11 (low): no lower bound for `a2a_termination_timeout`

`1us` is accepted and makes every termination unconfirmed. The smoke test
uses this on purpose to reach quarantine. Suggest a floor of 1 s in
`internal/config/a2a_options.go`.

## Smoke run 1 notes

The unexplained removal (Observations) came from `step_kill9_reconcile`
while the script still killed a wrapper shell instead of enclave, so the
joining process lived. Its log:

```text
a2a adapter: serving a2a-i2-smoke-k1 on 0.0.0.0:41821
a2a adapter: control connection: Get "http://a2a.enclave:41820/_enclave/control": dial tcp4 172.18.0.94:41820: connect: no route to host
a2a adapter: control connection: Get "http://a2a.enclave:41820/_enclave/control": dial tcp4: lookup a2a.enclave on 127.0.0.1:53: no such host
```

and the reconcile printed `removed member a2a-i2-smoke-k1: join did not finish`.
