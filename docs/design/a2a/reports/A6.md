## API

All functions go through the existing `capture` helper, so they follow
`docker.SetBinary` (docker or podman) and return `*cliError` for engine
failures.

| Symbol | Behavior |
| --- | --- |
| `NetworkConnect(ctx, network, container, ipv4 string, aliases ...string) error` | `network connect --ip <ipv4> [--alias a]... <network> <container>`. `ipv4` must parse as an IPv4 address (no CIDR) and is required. Already attached with the same static address: success. Already attached with another or an unverifiable address: `*EndpointConflictError`. Any other failure except missing container or network: a rollback `network disconnect` runs (see engine differences), then the original error is returned, joined with `ErrStaleEndpoint` if inspect still lists the endpoint. |
| `NetworkDisconnect(ctx, network, container string, force bool) error` | `network disconnect [--force] <network> <container>`. Not connected, missing container and missing network are success, so teardown and GC can call it unconditionally. |
| `SignalContainer(ctx, container, signal string) error` | Normalizes `HUP`, `SIGHUP`, `sighup`, `RTMIN+3`, `1` to the bare upper-case name, rejects anything else before invoking the CLI, then calls the existing `ContainerSignal` (`kill --signal`). `SignalReload = "HUP"`. |
| `ContainerNetworkEndpoints(ctx, container) (map[string]ContainerNetworkEndpoint, error)` | `container inspect --format '{{json .NetworkSettings.Networks}}'`, keyed by network name. `StaticIPv4()` returns `IPAMConfig.IPv4Address` (Docker) or the live `IPAddress` (Podman). |
| `EndpointConflictError{Network, Container, Want, Have}` | `Have` is empty when the address cannot be verified: a dynamic Docker attachment (no `IPAMConfig`) or a stopped Podman container. |
| `ErrStaleEndpoint` | Failed connect whose endpoint config survived the rollback. |
| `IsAddressInUse`, `IsStaticAddressRejected`, `IsUnattachableNetworkMode`, `IsNetworkNotFound`, `IsContainerNotRunning` | Error classifiers, texts below. The existing `IsNotFound` covers a missing container on connect, disconnect and kill. |

Network lookup in inspect output matches the name key first, then
`NetworkID` equality or a prefix of at least 12 characters, so A7 can pass a
network name or ID. Docker keys by name; Podman's `NetworkID` is the name.

## Engine differences (Docker 29.9.2, Podman 4.9.3 rootless, netavark)

1. **Initial network of an attachable container.** Docker refuses to connect a
   container started with `--network none`. Rootless Podman refuses a container
   on its default `slirp4netns` network and on `--network none`. Docker accepts
   `create --network none`, `network disconnect none`, connect, start; Podman
   rejects that sequence (`"" is not supported: invalid network mode`). So the
   hub must start on a bridge network on both engines. Both engines let a
   running container drop its initial bridge, go to zero networks, and attach
   again (verified with a running container on each engine). See CR-A6-1.
2. **Failed connect leaves endpoint state behind (both engines).**
   - Podman: after an IPAM failure (address in use, address outside the
     subnet) the attachment is recorded anyway. Later connects report "already
     connected", and `container inspect` fails with `network inspection
     mismatch`. A `network disconnect` clears it, although it exits 125 with a
     netavark `No such device` error. `NetworkConnect` rolls back, and the
     tagged test confirms the container reconnects and restarts cleanly.
   - Docker: after `Address already in use` on a running container,
     `NetworkSettings.Networks` keeps the network with the requested
     `IPAMConfig` and empty `NetworkID`. `network disconnect` (with or without
     `--force`) answers "is not connected". A restart re-applies the stale
     config: `failed to set up container networking: Address already in use`,
     and the container does not start. If the address has been freed by then,
     the container would instead join the network. The stale entry goes away
     when a later connect to the same network succeeds (it overwrites it), or
     on a disconnect once the container is stopped. `NetworkConnect` reports
     this as `errors.Is(err, ErrStaleEndpoint)`. The out-of-subnet failure
     leaves nothing behind on Docker.
3. **Idempotency evidence.** Docker records the static address in
   `IPAMConfig.IPv4Address` even while the container is stopped. Podman leaves
   `IPAMConfig` null and reports `IPAddress` only while running, so a repeated
   connect to a stopped Podman container yields `EndpointConflictError` with
   empty `Have`.
4. **Static address after restart.** Kept on both engines (tagged test).
5. **Exit codes.** Docker exits 1 for daemon errors and 125 for CLI flag
   errors; Podman exits 125 for everything. Classification is by stderr only.
6. **Podman IPAM leak.** When netavark teardown fails (seen while probing
   without the rollback), the allocation stays in the rootless
   `$XDG_RUNTIME_DIR/containers/networks/ipam.db`, keyed by network name. It
   outlives `network rm` and was hit again by a later network re-created
   under the same name: `requested ip address 10.250.67.5 is already allocated
   to container ID <removed container>`. The database lives on tmpfs and is
   cleared at reboot. One such leftover entry for the probe network name
   `a2a-a6-probe-home` remains on this host from probing.

### Q4 (static `--ip` without a user-configured subnet)

Not reproduced. On both engines a user-defined bridge network created
without `--subnet` accepts a static `--ip` inside its engine-allocated
subnet: Docker 29.9.2 on `172.20.0.0/16` and Podman 4.9.3 on `10.89.4.0/24`
(tagged test `TestEngineNetworkConnectStaticAddressOnDefaultIPAM`). The only
user-defined-network refusal seen was on Docker's default `bridge`
network: `user-specified IP address is supported on user-defined networks only`.
The wording `user specified IP address is supported only when connecting to
networks with user configured subnets` is from older Docker releases. It was
not observed here, but `IsStaticAddressRejected` matches it, together with
both engines' out-of-subnet texts. A7 can keep the rejection as a guard for
older engines. The static address must lie inside the engine-allocated
subnet, which A7 reads from `NetworkInspect(...).SubnetConfigs()`.

## Change requests

- **CR-A6-1 (against the proposal section 5 wording and A7).** "The hub has
  no network of its own" cannot be realized as `--network none` (Docker) or
  the rootless default network (Podman): neither can be connected afterwards.
  Proposed: A7 starts the hub with `--network <first member bridge> --ip
  <static hub address>`. It then attaches further members with
  `NetworkConnect` and drops the first bridge with `NetworkDisconnect` like
  any other member; both engines allow a running container to drop its
  initial network. A dedicated per-group placeholder network would also work,
  but it adds a network that the topology tests would have to prove is
  unreachable. No change is needed in A6's files.

## Open items for A7

- Choose a free hub address before connecting rather than relying on failure
  (for example from `NetworkInspect(...).Containers` and the gateway's
  address). A failed connect on Docker can leave `ErrStaleEndpoint` state that
  breaks the next hub restart. Recovery: a successful connect to the same
  network with another address, or a disconnect while the hub is stopped.
  Reconcile should treat a hub endpoint with empty `NetworkID` while the hub
  is running as stale.
- On Podman, `IsAddressInUse` naming a container ID that no longer exists
  indicates the IPAM leak above (engine difference 6), not a live conflict.
- `NetworkDisconnect` treats a missing network as success. If A7 needs to tell
  "already gone" apart from "disconnected now", it can inspect first with
  `ContainerNetworkEndpoints`.
- `EndpointConflictError` with empty `Have` on a stopped Podman hub: the hub
  should be running when connects happen, or A7 disconnects and reconnects.
- The existing `ContainerSignal` is kept; `SignalContainer` only adds
  validation. A signal is a nudge, never an acknowledgment (proposal 15), so
  `IsContainerNotRunning` is for logging and reconcile decisions.
