# A11 report: MCP client

Package A11, Wave 2. Branch `a2a-a11`, based on `6fdb667`. Owned files:
`internal/a2aagent/mcp/`, `cmd/enclave-a2a-agent/mcp.go`,
`cmd/enclave-a2a-agent/client.go`, their tests, and this report.

## Summary

- `internal/a2aagent/mcp` (standard library only; imports `internal/a2a` and
  `internal/a2aagent`):
  - `Client`: the four operations (`ListPeers`, `Send`, `Get`, `Cancel`),
    `HoldLiveness`, and the send journal. MCP and the CLI share it.
  - `Server`: hand-written newline-delimited JSON-RPC over stdio, implements
    `a2aagent.MCPClient`. It holds the liveness connection while `Serve`
    runs.
  - `Journal`: the durable send journal (CR-P3-2).
- `enclave-a2a-agent mcp [--journal-dir <dir>]`: the stdio MCP server.
- `enclave-a2a-agent client [--journal-dir <dir>] peers|send|get|cancel|hold`:
  the CLI fallback. It prints the same JSON as the tools and uses the
  section 10 exit codes (0, 1, 2 usage, 4 wait elapsed, 5 other terminal
  state, 130 interrupted). `hold` holds the liveness connection for tools
  without MCP (see notes for A15).

Wire behavior (interfaces section 11):

- Every request carries `Authorization: Bearer <inbound token>`,
  `A2A-Version: 1.0` and `A2A-Extensions: <ExtensionURI>`. Dials use IPv4,
  and `Transport.Proxy` is nil because the session env may carry
  `HTTP_PROXY`.
- A send first fetches `/_enclave/peers`. That validates the peer and gives
  the worker generation for the handle (the hub never sends it otherwise).
  It then journals the send and posts `SendStreamingMessage` to
  `/peers/<peer>`. SSE and plain JSON responses are both accepted. A
  JSON-RPC error inside the stream ends it.
- When a stream ends before a terminal state, the client resubscribes with
  `SubscribeToTask` (1 s backoff after a failure). `-32004` on a terminal
  task falls back to `GetTask`. Dropping or abandoning a stream never sends
  `CancelTask`; only `cancel_task` does.
- Liveness: `GET /_enclave/liveness` must start with a `hello` event. Any
  byte (keepalive comments included) resets a 30 s idle watchdog (two 15 s
  keepalives). Reconnect backoff is 1 s, doubling to 10 s, and resets after
  a connection that lasted at least 30 s.

MCP handshake (P3 facts 1 to 4): `server/discover` and every other unknown
request get `-32601`. `initialize` echoes `2025-11-25`, `2025-06-18`,
`2025-03-26` or `2024-11-05` and answers anything else with `2025-11-25`.
Capabilities are `{tools: {}}`. `tools/call` runs concurrently. A call ended
by `notifications/cancelled`, by stdin EOF or by a signal gets no response
and is never a cancellation. `notifications/progress` is sent at most every
30 s, and only when `_meta.progressToken` is present. An unknown tool is
JSON-RPC `-32602`. Bad arguments (unknown fields, a negative
`wait_seconds`) return a tool result with `isError: true`.

## Tool definitions as shipped

```json
{"tools":[{"name":"list_peers","description":"List worker peers.","inputSchema":{"type":"object","properties":{}}},{"name":"send_task","description":"Send a task to a worker; waits for its final message. If the wait ends first, returns the handle (the task: value, not a Claude task ID); the task continues, use get_task. retry=true only to resend one whose outcome you lost (same peer, text, context).","inputSchema":{"type":"object","properties":{"context":{"type":"string","description":"ctx: handle, to continue"},"message_id":{"type":"string"},"peer":{"type":"string"},"retry":{"type":"boolean"},"text":{"type":"string","description":"full task; worker lacks your context"},"wait_seconds":{"type":"integer"}},"required":["peer","text"]}},{"name":"get_task","description":"Task state and final message; waits up to wait_seconds (0: now). No handle: recent sends.","inputSchema":{"type":"object","properties":{"handle":{"type":"string","description":"task: handle"},"wait_seconds":{"type":"integer"}}}},{"name":"cancel_task","description":"Cancel a task.","inputSchema":{"type":"object","properties":{"handle":{"type":"string","description":"task: handle"}},"required":["handle"]}}]}
```

**Cost: 1,186 bytes**, down from P3's 1,669 bytes (−29 %). That is
**about 340 tokens** at 3.5 bytes per token, which is the "few hundred" of
proposal 21. Upper bound: P3 measured 1,021 tokens for its 1,669 bytes in a
`--tools ''` baseline, which includes Claude Code's one-time tool-use
framing. Scaled linearly, that gives at most about 725 tokens. In a normal
session other tools already pay that framing, so the marginal cost is
closer to the byte estimate. `TestToolDefinitionBudget` fails above
1,200 bytes. Not measured against a real Claude Code run; I2 can confirm
with P3's `run.sh` (r0 against the baseline).

Trimming choices: the result fields are self-describing, so the schema
documents only `text`, `context` and `handle`. The two statements the model
needs are kept: the handle is the `task:` value, not a Claude task ID, and
`retry` is only for a send whose outcome was lost.

## Result shape

Every tool returns one JSON object in a single text content item. The
fields are omitted when empty:

| Field | When |
| --- | --- |
| `handle` | `task:<worker>:<workerGeneration>:<taskID>`, once the first stream event arrived |
| `state` | A2A enum name (`TASK_STATE_*`) |
| `queuePosition` | while `TASK_STATE_SUBMITTED` (0 is next) |
| `messageId` | send results, and get/cancel results for journaled handles |
| `context` | `ctx:` handle of the task's context |
| `reason`, `termination` | from `metadata[ExtensionURI]`, as set by the adapter |
| `message` | final text on a terminal state; artifacts first, else the terminal status message |
| `error` | `isError: true`; enclave and A2A errors render as `<message> [<code> <REASON>]` |
| `note` | wait elapsed ("the task continues"), outcome unknown (how to retry), recovery hints |
| `peers` | `list_peers` (`name`, `description`) |
| `recent` | `get_task` without a handle: up to 10 newest journal entries |
| `candidates` | ambiguous or mismatched retry |

A `get_task` argument that does not parse as a task handle answers with
the hint that handles are `task:` values and not Claude task IDs, and
that `get_task` without a handle lists them (P3 fact 7).

## Send journal

Location: `<journal dir>/journal.json`, with `journal.lock` next to it
(flock). The directory comes from `--journal-dir`, then
`ENCLAVE_A2A_TABLE_DIR` (CR-A11-1), and the client refuses to start
without one. The directory is created 0700 and the file is written 0600.
Every write is atomic (temp file, fsync, rename) under the lock, so the MCP
server and a concurrent `client` invocation serialize.

```json
{
  "schemaVersion": "1",
  "group": "review", "groupGeneration": "…", "member": "lead", "memberGeneration": "…",
  "updatedAt": "2026-11-05T10:00:00Z",
  "entries": [{
    "messageId": "uuid-v4",
    "peer": "builder",
    "context": "ctx:… as sent (retry match key), empty for a new context",
    "contextHandle": "ctx:… the task ran in",
    "contentHash": "sha256:<hex of text>",
    "handle": "task:…",
    "state": "TASK_STATE_WORKING",
    "reason": "", "termination": "", "error": "",
    "attempts": 1,
    "sentAt": "…", "updatedAt": "…"
  }]
}
```

- The entry is written before the request leaves the client. The handle
  and context are written as soon as the first event arrives, and the
  state after each operation returns. `get_task` and `cancel_task` update
  entries by handle.
- An unknown `schemaVersion` or invalid JSON is an error (fail closed).
- A file whose header names another group, group generation, member or
  member generation counts as empty and is overwritten on the next write.
  Its message IDs and handles are unusable under the new principal anyway
  (the adapter answers `-31013` or `-32001`).
- Bound: 100 entries, oldest dropped first. The entry being sent is moved
  to the end, so the bound never evicts it.
- Only the content hash is stored, never the task text.

## Retry resolution rules

| Arguments | Behavior |
| --- | --- |
| no `retry`, no `message_id` | new UUID message ID, new entry; never flagged |
| `message_id` without `retry: true` | local error; an unflagged reuse would only earn `-31012` |
| `retry: true`, `message_id` found in the journal | peer, text hash and context must match the entry, else a local error listing it; then resend with that ID and `metadata[ExtensionURI].retry = true`, `attempts` + 1 |
| `retry: true`, `message_id` not in the journal | sent flagged with that ID; the adapter decides (attach, known outcome, or `-31013`) |
| `retry: true`, no `message_id`, one entry with the same peer, text hash and context | resend with its message ID, flagged |
| same, no matching entry | local error: nothing to retry, send without `retry` |
| same, several matching entries | local error with `candidates` (handle, state, messageId, sentAt); pass `message_id` |

A failure before the task ID arrived (transport error, stream closed, no
task ID within the wait plus 30 s) returns `error`, the `messageId`, and a
note that tells the model how to retry. A JSON-RPC refusal before
admission (for example `-31016`) is reported as an error. The entry keeps
the message ID either way.

## Wait bounds

- `ENCLAVE_A2A_SEND_WAIT` (`Config.SendWait`) defaults to 90 s when zero
  (CR-P3-1). The model's `wait_seconds` is clamped to `[0, SendWait]`.
- `send_task` always waits for the first event, so it holds a handle even
  with `wait_seconds: 0`.
- `get_task` blocks up to the same bound by default. `wait_seconds: 0`
  returns at once.
- The CLI's `--wait` takes Go duration syntax and is clamped the same way.
- `ENCLAVE_A2A_MAX_REQUEST_BYTES` defaults to 1 MiB and is checked locally
  before journaling.

## Change requests

- **CR-A11-1** (2026-11-05, A11, section 6): the orchestrator needs a
  journal directory in its config store, and section 6 has no variable for
  it. Proposed: set `ENCLAVE_A2A_TABLE_DIR` for orchestrators as well. Its
  value is the container path of `<config store>/a2a/<memberGeneration>/`,
  the same shape as the worker's table directory. The client writes
  `journal.json` and `journal.lock` there. Change the Roles column to
  "both"; no new name is needed. Inventory deletion (A2) and the generation
  scoping of D4 then cover the journal by construction. I1 sets the
  variable and creates the directory, and A10's `LoadConfig` must not
  reject `TableDir` for the orchestrator role. Alternative if the
  coordinator wants separate names: a new `ENCLAVE_A2A_JOURNAL_DIR` with
  the same value. Until decided, the client reads `--journal-dir` first,
  then `Config.TableDir`, and refuses to start without either.
- **CR-A11-2** (2026-11-05, A11, section 6 and P13, for A15 and I1): the
  CLI fallback cannot hold liveness, because each invocation is
  short-lived. An orchestrator on a tool without MCP would be suspected
  departed after the reconnect window. Proposed: such sessions run
  `enclave-a2a-agent client hold` in the background for the session's
  lifetime (entrypoint or I1), next to the CLI calls. MCP sessions need
  nothing, because `mcp` holds liveness itself. No interface change for
  Claude Code (v1's only tool), so this is a note unless another
  orchestrator tool ships.

## Notes for A10

- `cmd` calls `a2aagent.LoadConfig(os.Environ())`. On the current `a2a` tip
  it is still the W0-B stub that panics, so `mcp` and `client` are
  non-functional until A10 merges (A10 merges before A11). For the
  orchestrator role `LoadConfig` should require `HubHost`, `HubPort`,
  `InboundToken`, `Member`, `MemberGeneration`, `Group` and
  `GroupGeneration`, and should accept `TableDir` (CR-A11-1). `mcp.New`
  checks these again.
- The client reads the final text from artifacts first, then from the
  terminal `status.message`. Either works; pick one and keep it.
- The client expects the first event of `SendStreamingMessage` and
  `SubscribeToTask` to carry the `Task` (`taskId` is also taken from a
  first status or artifact update). It relies on `queuePosition`,
  `reason` and `termination` under `metadata[ExtensionURI]` on `Task` and
  terminal status events.

## Notes for A15 (wiring)

  `context` values, use `get_task` (no arguments) to recover lost handles,
  and use `retry: true` only after a lost result.

## Open items
