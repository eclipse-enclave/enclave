# A14 report: A2A agent image variant and serve-mode launch

Branch `a2a-a14`, rebased onto `a2a` at `e894ddd` (A3, A4, A10 and A11
merged). This is the second rework after the Wave 2 decisions.

## Summary

- **Variant selection**: `model.BuildOptions.A2AAgent` (not an option) is
  set in `ValidateRunOptions` from `opts.PeerGroup != ""`. It flows into
  `runtimeImageSelection.A2AAgent` and `resolveBuildConfig`. The variant's
  image name prefixes the tag with `a2a-` (`enclave-claude:latest` becomes
  `enclave-claude:a2a-latest`). An explicit `--image-name` is kept as given.
  Other build-config fields are unchanged.
- **Variant Dockerfile** (`withA2AAgentBuild`): applied after the normal
  render, only for the variant, in both the rebuild-hash path and
  `buildImage`. It makes three insertions, and each anchor must occur
  exactly once:
  - Before `FROM feature-base AS standard`, a stage
    `FROM <golang pin> AS a2a-agent-build`. The stage copies the manifest
    paths and `runtime-assets/a2a-agent`, runs the installer, and
    `install -m 0755` the wrapper into `/out`.
  - Before `COPY entrypoint.sh` (the most volatile layer), the line
    `COPY --from=a2a-agent-build /out/ /usr/local/bin/`.
  - In place of `ENTRYPOINT ["/usr/local/bin/entrypoint.sh"]`, the line
    `ENTRYPOINT ["/usr/local/bin/enclave-a2a-entrypoint"]`.
- **Serve mode through the wrapper**: `runtime-assets/a2a-agent/enclave-a2a-entrypoint`
  (POSIX sh) runs `exec entrypoint.sh enclave-a2a-agent serve` when
  `ENCLAVE_A2A_ROLE=worker`, so all of the entrypoint's session setup
  still runs. With the role unset or `orchestrator` it runs
  `exec entrypoint.sh "$@"`; any other role exits 1. Tests point it at the
  repository's `entrypoint.sh` through `ENCLAVE_A2A_ENTRYPOINT`, the same
  override pattern as the entrypoint's library paths. `entrypoint.sh` is
  byte-identical to `a2a`. Runtime UID remap still works, because the
  entrypoint's `sudo -E "$0" "$@"` re-exec keeps the adapter command.
- **Variant hash**: the combined hash gets `-a2a-agent-<hash>` appended,
  covering `runtime-assets/a2a-agent/` and
  `internal/app/a2a_agent_build_inputs.txt`. The manifest now holds what
  `go list -deps ./cmd/enclave-a2a-agent` reports (CR-A14-3 accepted):
  `go.mod`, `go.sum`, `cmd/enclave-a2a-agent`, `internal/a2a`,
  `internal/a2aagent`, `internal/buildinfo`, `internal/logx`,
  `internal/model`, `internal/tools`, `internal/util`. `go.sum` is required
  because the agent links `golang.org/x/sys/unix` and `golang.org/x/term`.
  The builder stage therefore downloads modules and needs network access
  during the build, like the gateway proxy's.
- **Manifest tests**:
  - every `enclave/...` package the agent links is listed
  - every listed path except `go.mod`/`go.sum` is linked
  - `go.sum` is listed exactly when a third-party module is linked
- **Regular images are byte-identical**:
  - `TestWithA2AAgentBuild` checks that the regular render has no `a2a`
    content.
  - `TestRegularImageHashIgnoresA2AAgent` checks that the repository's
    `entrypoint.sh` has no A2A handling.
  - The same test recomputes the pre-A14 hash formula and shows that
    editing the agent sources, `go.mod`, the installer or the wrapper
    leaves the regular hash unchanged while changing the variant's.
  - Regular image names are unchanged.
- **Assets live in `runtime-assets/a2a-agent/`**, outside `build-scripts/`.
  `build-scripts/` is copied into every image and hashed as a static input,
  so placing them there would change regular images.
- **CR-A14-1 (embedding and packaging)**:
  - `assets_embed.go` embeds `all:cmd/enclave-a2a-agent`, `all:internal/a2a`,
    `all:internal/a2aagent`, `all:internal/buildinfo` and
    `all:internal/tools`.
  - `assets_test.go` checks every entry of both build-input manifests.
  - `debian/rules`, `packaging/rpm/enclave.spec` and
    `scripts/verify-package-assets.sh` iterate over both manifests.
  - `runtime-assets/` ships whole, as before.

## Worker permissions

No wiring in A14. When the session resolves yolo, `internal/runtime/runtime.go`
already sets `ENCLAVE_YOLO=1`. The adapter reads it and appends the spec's
`yoloFlag` (follow-up package). I1 rejects `--role worker` without yolo
using `resolveYoloEnabled` in `internal/app/command_run.go`.

## CR-A14-3 (accepted, deferred)
